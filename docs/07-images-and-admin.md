## 12. Image upload / storage architecture

- **Buckets:** `ik-images` (public via custom domain `img.<domain>`, never `r2.dev`) and `ik-backups` (private). Separate dev/staging buckets.
- **Why direct-to-R2 uploads:** Vercel functions have a small request-body limit (~4.5 MB _(verify)_) and we don't want image bytes through our function CPU. The browser uploads straight to R2 with a presigned URL.
- **Flow:**
  1. The admin UI resizes/compresses each image to WebP (max ~2000 px) **in the browser**.
  2. `POST /api/admin/uploads/sign` (`requireAdmin()`): validates productId, content-type allow-list (jpeg/png/webp) and declared size ≤ 5 MB; returns a **presigned PUT URL** (short expiry, content-type and content-length signed in) for a random key `products/{productId}/{ulid}.webp`, using S3-compatible credentials scoped to that bucket.
  3. The browser `PUT`s the file to R2 (bucket CORS allows PUT from the site origin only).
  4. `POST /api/admin/uploads/commit` (`requireAdmin()`): server `HEAD`s the object (size/type), range-reads the first bytes to **verify magic bytes**, then inserts the `product_images` row with alt text (required), dimensions and sort order. Objects that fail verification are deleted.
  5. A weekly sweep (`/api/cron/sweep`) deletes objects with no DB row older than 24 h.
- **Serving:** immutable `Cache-Control` (keys are never reused), CDN-cached at `img.<domain>`; custom `next/image` loader (§15).
- **Deletion:** soft-delete rows; purge R2 objects after 30 days (R2 has no per-object recovery, so this is the safety net).

## 13. Admin panel architecture

Route group `/admin` with its own layout, `noindex`, **`requireAdmin()` in every page/action/handler**, server-side pagination, Server Actions + Zod, and an `audit_log` entry per mutation.

| Module       | Scope (v1)                                                                                                                                                                                                                         |
| ------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Dashboard    | today/7d/30d orders and revenue, orders needing action (paid → processing), low-stock list. SQL aggregates cached ~60 s                                                                                                            |
| Products     | list/search/filter; create/edit; **variant matrix generator** (sizes × colors → SKUs); per-variant price/stock; image upload + reorder + alt text; draft/active/archived (never hard-delete products that have orders)             |
| Categories   | flat list (no sub-categories), drag-to-reorder, visible toggle (hides its products too), product counts, delete when empty                                                                                                         |
| Inventory    | per-variant grid, inline adjust with reason, movement history                                                                                                                                                                      |
| Orders       | filters by status/date/search; detail; transition buttons; add courier + tracking; refund (full/partial); internal note; printable packing slip / invoice (print-CSS HTML)                                                         |
| Customers    | list with search, status filter and sortable per-customer stats (orders, total spent, last order); detail (addresses, recent orders, "View all orders"); disable/re-enable account (blocks sign-in, signs out everywhere)          |
| Coupons      | CRUD: type, value, min subtotal, max discount, date-only validity window, global and per-user limits; list with code search, derived-status filter/badge, sortable columns, creator + created time; confirmed active toggle        |
| Settings     | shipping fee/threshold, GSTIN/seller state, contact details, business address, social links, products & stock defaults (low-stock threshold, default GST) — split into per-section rows, no card chrome                            |
| Activity log | not in the original v1 scope, added alongside it: every admin mutation read back from `audit_log` (§13's own logging), filterable by area/admin/date range, each row expandable to a before/after diff and the raw stored snapshot |

Stack: shadcn/ui, a small bespoke server-driven `DataTable` (`src/app/admin/_components/data-table.tsx` — TanStack Table was tried in Phase 11 and dropped, see its notes), react-hook-form + Zod. UI conventions and the reasoning behind them (tables, filters, sorting, confirmations, accent use, dates) are recorded in `.impeccable.md` → "Established patterns (admin)". Admin-only heavy libraries are code-split so they don't add to storefront bundles. Admin pages are never cached.

## Implementation notes (Phase 7 — backend only, no `/admin` pages yet; built and verified against real Postgres + the real R2 dev bucket, per docs/09 §20)

- **Every admin mutation function returns `{ result, revalidateTags }`, never calls `revalidateTag` itself.** `revalidateTag` only works inside a real Next.js request context, not in a plain test or script — `server/modules/admin/types.ts`'s `AdminMutationResult<T>` is the shared shape; the eventual Phase 11 Server Action is what actually calls `revalidateTag(...)` with the tags returned.
- **`server/modules/admin/audit.ts`'s `writeAuditLog` always runs inside the same transaction as the mutation it records** — verified for every domain (categories, products, variants, images, inventory, coupons, customers, orders, settings) rather than assumed.
- **A new `db/schema/relations.ts` was needed for the customer/order admin views** (`user` ↔ `addresses`/`orders`, `orders` ↔ `items`/`payments`/`events`/`refunds`, `coupons` ↔ `redemptions`) — `auth.ts` and `commerce.ts` each need relations pointing at the other, and defining `relations(user, ...)` directly in commerce.ts (which already imports `user`) would need auth.ts to import back, a real circular module dependency. One central file avoids it. Confirmed the hard way that Drizzle does **not** merge two separate `relations()` calls for the same table across files — a second one for `productVariants` silently replaced catalog.ts's existing relations instead of adding to them, breaking `cart/quote.ts`'s typing until reverted to a one-directional `inventory -> variant` relation instead.
- **Inventory admin (`inventory/admin.ts`'s `adjustStock`)** mirrors `on_hand + delta >= reserved` in its `WHERE` clause, which covers both CHECK constraints (`on_hand >= 0`, `reserved <= on_hand`) in one condition, since `reserved` is itself always `>= 0`.
- **Orders admin adds the `paid`/`processing -> cancelled` path Phase 6 deliberately deferred** (`orders/admin.ts`'s `cancelPaidOrder`): always a full refund of whatever's unrefunded, plus `inventory/service.ts`'s new `returnSoldStock` (the inverse of `sellReservedStock` — only `onHand` moves, since `reserved` was already cleared at sale time). `refundOrder` is the separate, more general action for "any paid state -> refunded," handling both a partial refund (status unchanged, `refundedPaise` grows) and a full one (transitions to `refunded`).
- **`store_settings.gstin` is deliberately left optional with no placeholder to replace** — docs/11 §29 #3 confirms the business isn't GST-registered, so a blank GSTIN is the actually-correct value, not a TBD.
- **A real environment limitation, not a code bug:** this machine's system clock is wrong — **measured 2026-09-25: 330 minutes (exactly 5 h 30 min) behind** R2's `Date` header, i.e. a Windows time-zone misconfiguration (the wall clock shows IST but the OS treats it as UTC), not a "future date" as first assumed. Cloudflare R2 rejects presigned URLs signed against it with `ExpiredRequest` (confirmed: a live AWS SDK call that signs-and-sends in one step succeeds against the real bucket; a presigned URL's signature, fixed at generation time and checked by R2 against its own real clock, always fails here regardless of how quickly it's used afterward). `media/uploads.ts`'s `signProductImageUpload` calls `getSignedUrl` exactly as Phase 0's already-approved spike (`scripts/phase0-r2-check.ts`) does — this is not expected to be a problem on Vercel's real clock. `tests/integration/media-uploads.test.ts` works around it by uploading via a direct `PutObjectCommand` instead of actually fetching the presigned URL, so `commitProductImageUpload`'s real server-side verification (HEAD, magic bytes, delete-on-failure) is still exercised for real against the real bucket — but **the presigned-URL hop itself has not been verified end-to-end in this environment** and should get a real manual check (e.g. from a browser, or from a machine with a correct clock) before launch. **Same root cause surfaced again building the orphan-image sweep** (below): comparing a local `Date.now()` cutoff against R2's own `LastModified` on a just-uploaded object showed the local clock still measurably behind R2's, so `sweepOrphanImages`'s test can't rely on `graceMs=0` to force "already past grace" — it uses a deliberately negative `graceMs` (pushing the cutoff into the future) instead, comfortably clearing the skew regardless of its exact size at test time. The production default (`ORPHAN_GRACE_MS`, 24h) is unaffected — a skew of minutes to hours is irrelevant against a day-long window.
- **Resolved since:** `/admin` pages themselves (Phase 11 — see "Implementation notes (admin UI …)" below); printable invoice HTML (`orders/[orderId]/invoice`); the weekly orphan-image sweep and webhook-event pruning, both now live under a single `/api/cron/sweep` endpoint (`media/sweep.ts`'s `runSweep` — orphaned `products/` R2 objects with no `product_images` row, older than 24h; `webhook_events` rows older than 90 days per docs/03 §4), same bearer-secret pattern as `/api/cron/reconcile`, verified against the real dev bucket and real Postgres. The dashboard's SQL aggregates (`windowStats`, `dailySeries`, `topCoupons`, `needsProcessing`, `lowStockList`) are now `"use cache"` functions with a `{stale:60, revalidate:60, expire:300}` `cacheLife` (`admin/(dashboard)/page.tsx`) — a short time-based cache, not tag-based: nothing in checkout/admin currently revalidates a dashboard-specific tag, and wiring one into every order/customer/coupon mutation path is real, untested surface this doesn't warrant yet. Verified: `next build` accepts every one of them with no Cache Components scope violation (a real, direct check, not an assumption — these were the first `"use cache"` functions in the codebase, `cacheComponents: true` had been enabled since Phase 0 but never actually exercised until now), and the route renders without error at runtime. **Not yet verified:** actual cross-request caching benefit on Vercel's real serverless runtime — Next's own docs note the default in-memory handler typically doesn't persist across separate invocations there, so the practical effect in production may be closer to build-time/same-instance reuse than a guaranteed 60s wall-clock cache; worth a real measurement once there's real traffic, not before.

## Implementation notes (admin UI — coupons, customers, lists)

- **`coupons.created_by_admin_id`** (migration `0005_coupon_created_by`) records which admin created each coupon, shown as "by <email>" under the list's Created column. Nullable with `ON DELETE SET NULL` — coupons seeded outside the admin UI have no creator, and removing an admin shouldn't take their coupons with them. The migration backfills existing rows from each coupon's `coupon.create` audit row (verified against real Postgres: only `coupon.create` rows match, coupons without one stay NULL). It's set only in `createCoupon`; `updateCouponInputSchema` doesn't accept it, so it can't be rewritten later.
- **The list's Status (Live / Scheduled / Expired / Used up / Inactive) is derived, not stored** — `coupons/status.ts`'s `couponStatusSql` is one SQL `CASE` used for both the badge and the status filter, so they can't disagree. Precedence: switched off → expired → used up → not started → live, with the same comparisons as `validate.ts`'s checkout eligibility. Covered by `tests/integration/coupons.test.ts`.
- **Real driver quirk, surfaced by that test:** a JS `Date` interpolated directly into a raw `` sql`...` `` template is _not_ serialized by the postgres-js driver — the query throws `ERR_INVALID_ARG_TYPE` ("The "string" argument must be of type string… Received an instance of Date"). Typed helpers like `lt(column, date)` are fine because Drizzle maps them through the column type; in raw `sql` fragments, bind `date.toISOString()` with a `::timestamptz` cast instead.
- **All admin dates are formatted in `Asia/Kolkata` explicitly** through `src/app/admin/_lib/format-date.ts` (`formatAdminDate` / `formatAdminDateTime`) — pages render in Server Components, which would otherwise use the host's timezone (UTC on Vercel). Coupons (Created) and Customers (Joined, Last order, order dates, "disabled … on") use it; older pages still call `toLocaleDateString()` and should move over when next touched.
- **Every admin list paginates in SQL at `ADMIN_PAGE_SIZE` = 20** (`server/modules/admin/pagination.ts`): Orders, Products, Customers (`CUSTOMERS_PAGE_SIZE` aliases it), Coupons, Inventory, and a variant's stock-movement history (previously a flat `limit: 100`). **Inventory previously loaded every inventory row and filtered/sorted/sliced in JS** — it now does search (`ilike` on product name/SKU/color), the low-stock filter (`on_hand - reserved <= 5`), ordering and paging in one joined query plus a count. Verified against the real dev DB: consecutive pages don't overlap, every low-stock row qualifies. Categories is paginated too (see its note below).
- **Column sorting** (Coupons, Customers so far) is URL-driven (`?sort=&dir=`) through `_lib/table-sort.ts` (`parseSort` / `sortLinkFor`) and `DataTable`'s optional `sortLinks` prop. `DataTable` is a client component, so pages pass **precomputed header hrefs**, never a callback. Each page has a fixed allowlist of sort keys; the direction reaches SQL via `sql.raw` only after being validated to exactly `asc`/`desc`. Every sort is `… nulls last` with `id` as a tiebreaker (stable pages). Verified on the real dev DB, including null "No cap" values staying last both ways.
- **Customer list stats** (`customers/queries.ts`'s `listCustomers`): orders count, total spent and last order date come from one grouped subquery over `orders` **where `paid_at IS NOT NULL`** — abandoned/unpaid checkouts don't count — with spend net of `refunded_paise` and summed as `bigint` (lifetime spend can outgrow int4 paise). Customers with no paid orders get 0 / "—" and sort last. `listCustomers` now parses its own input through `listCustomersInputSchema` (status filter, sort key allowlist, direction). Covered in `tests/integration/admin-misc.test.ts`.
- **"Disabled by … on …"** on the customer detail page is read back from the latest `customer.disable` `audit_log` row (joined to the admin's email) — no new column needed, since `setCustomerDisabled` already writes that row in the same transaction. Disabling now also deletes the user's sessions and blocks sign-in (see docs/04 §5).
- **Coupon validity is date-only.** The dialogs send a start date as local 00:00:00 and an end date as local 23:59:59.999, so the end date is inclusive. `new Date("yyyy-MM-dd")` alone would parse as **UTC** midnight — `DatePickerField`'s `parseDateValue` builds local dates explicitly. The Edit dialog previously displayed stored times via `toISOString()` (UTC), which could show the wrong day in IST; also fixed.
- **Real framework quirk — Next 16 `cacheComponents` preserves client state across navigations** (React `<Activity>`, `node_modules/next/dist/docs/01-app/02-guides/preserving-ui-state.md`): pages/layouts are hidden, not unmounted. The sign-out confirmation dialog's `open` state survived sign-out → sign-in and reopened immediately after logging back in. Fixed with the docs' own pattern (reset transient state in a `useLayoutEffect` cleanup, `admin-shell.tsx`). Any dialog/popover whose action navigates away needs the same treatment.
- **Real component quirk — the shadcn `Switch` has an invisible enlarged hit area** (`after:absolute after:-inset-y-2`, 8px beyond the switch). As the last child of a scroll container it overflowed by a few px and forced a phantom scrollbar in the New coupon dialog. That switch is gone now, but any scroll container ending in a `Switch` needs ≥8px bottom padding.
- **`DialogFooter` can't live inside a scrolling area** — its negative margins (`-mx-4 -mb-4`, to bleed to the dialog edge) overflow the scroll container and add both scrollbars. Keep the footer a sibling of the scrolling field area, as `CreateCouponDialog` does.
- **Dashboard: New customers and Coupons used.** The metric strip and a 2×2 trend grid now cover orders, revenue, new customers (`user.role = 'customer'` by `created_at`) and coupon uses (a muted second line gives the discount total), plus a "Top coupons" card (5 most-used codes in the range, linking to the Coupons list filtered by code). Coupon figures count a `coupon_redemptions` row only when its order has `paid_at` set — the same rule as Revenue — because a redemption is written at order creation and only removed on cancel/expiry, so a still-pending checkout would otherwise count. Demo data: `src/server/db/seed-dashboard-activity.ts` (40 spread-out signups; coupons applied to ~⅓ of the order seed's paid orders with real redemption rows and consistent order totals).
- **Dashboard dates are store-time (IST), not server-time.** `src/app/admin/_lib/store-time.ts` computes "today", "7 days", "1/3 months", custom-range bounds and per-day chart buckets in `Asia/Kolkata` whatever zone the host runs in — previously `setHours(0,0,0,0)` and `date_trunc('day', …)` used the server/DB session zone (UTC in production), so "Today" would have rolled over at 05:30 IST and late-evening orders landed on the next day's bar. The custom range's `from` was also parsed with `new Date("yyyy-MM-dd")` (UTC midnight); now `startOfStoreDay`. SQL buckets use `storeDaySql`, which also handles Better Auth's `timestamp`-without-tz columns (UTC wall time, marked `at time zone 'UTC'` before converting). Verified: unit tests pass under both `TZ=UTC` and `TZ=Asia/Kolkata`, and on the dev DB all 124 order/user rows bucket identically in SQL and JS with the process in UTC (12 of them fall in the 18:30–24:00 UTC window the old code misassigned). The Orders list's From/To filter had the same `new Date(from)` UTC bug — **fixed** with the Orders page rework (below).
- **Categories are flat** (migration `0006_flatten_categories`): `parent_id`, its index, FK and the self-relation are gone, along with the service-side 1-level-nesting check and the admin form's "Parent category" field. Nothing was deleted — former sub-categories became regular categories; the migration first renumbers `sort_order` across the whole list so each former child sits right after its old parent (dry-run on the dev DB inside a rolled-back transaction confirmed the order). This also removes the open storefront question of whether a parent category page should include its children's products.
- **Test-harness quirk:** every integration test file runs `migrateTestDb()` in its own `beforeAll`, and Vitest runs files in parallel. The first run after a new migration lands, several files apply the same `ALTER TABLE` concurrently and Postgres reports `deadlock detected` (40P01) — not a bug in the migration. Running one integration file first (or a clean run once the migration is applied) passes; worth moving migration into a Vitest `globalSetup` so it runs once.
- **Hiding a category hides its products on the storefront** (nothing is deleted; they come back when it's shown). One rule applied in all four places a shopper can reach a product: `catalog/queries.ts` listing/search and facets (an `EXISTS` on a visible category, `inVisibleCategory`), the PDP (`catalog/service.ts`'s `getProductDetail` → 404), and `cart/quote.ts` (line becomes `unpurchasable`) — which `checkout/createOrder.ts` reuses, so a product already sitting in a cart can't be bought either. Covered by `tests/integration/catalog.test.ts` ("hidden categories"). Previously hiding a category only removed its own page; its products stayed in "all products" and search.
- **Categories admin page**: shared `DataTable`; a Products column (count, linking to `/admin/products?category=<id>`); the switch column is "Visible" and confirms both ways, naming the effect and product count; the form no longer shows the "Image key (R2 object key)" field — the `image_key` column stays, and edits no longer send it, so any existing value is untouched until the storefront actually uses category images.
- **Deleting a category is allowed only while it has no products** (`catalog/admin.ts`'s `deleteCategory`, audited as `category.delete`): a product count check throws `CategoryNotEmptyError` ("… still has N products — move or delete them first"), and `products.category_id`'s `ON DELETE RESTRICT` is the backstop for a product added concurrently (a Postgres `23503` is mapped to the same error). In the admin, the trash button is disabled with that reason as a tooltip while the category has products, and confirms in the destructive style otherwise. Covered in `tests/integration/catalog-admin.test.ts`. The dev DB's leftover test sub-category ("saree sub", 0 products) was deleted the same way, with an audit row.
- **Drag-to-reorder** (`_components/sortable-data-table.tsx`, on dnd-kit: `@dnd-kit/core`, `/sortable`, `/modifiers`, `/utilities`) replaced the Categories ↑/↓ arrows. Rows move by a grip handle only (so switches/buttons in the row still click normally), with mouse, touch and keyboard support and screen-reader announcements; the new order shows instantly and is saved via the existing `moveCategoryAction` → `reorderCategories`, snapping back with an error toast if the save fails. `DndContext` gets a React `useId()` because dnd-kit's own accessibility ids come from a module counter that can differ between SSR and hydration. Reusable for other hand-ordered lists (e.g. product images).
- **Categories now have search (name/slug), column sorts (Name, Slug, Products) and pagination (20/page) alongside drag-to-reorder.** The default view is "store order" (`sort_order`), the only view with drag handles; any column sort swaps to the plain `DataTable` with a "Back to store order" link. To make dragging work on a single page or in search results, `reorderCategories` now takes the ids of **just the visible rows** in their new order: they swap among the slots they already occupy, everyone else keeps their place, and the whole table is renumbered `0..n-1` (rows locked `FOR UPDATE` so concurrent reorders can't interleave; unknown/duplicate ids rejected). `createCategory` now appends at `max(sort_order) + 1` instead of defaulting everything to 0, which had produced ties. `DataTable`'s header cell was extracted as `DataTableHead` so `SortableDataTable` shares the sort-link headers. Covered in `tests/integration/catalog-admin.test.ts` ("category order").
- **Product pages simplified for a non-technical owner.** (1) **Adding sizes & colours**: preset size chips (XS–3XL, Free size) + custom sizes, colour name + swatch, and a **starting-stock grid** (one box per new size × colour); `generateVariantMatrix` now takes optional `startingStock` (each quantity > 0 also writes a `restock` stock movement noted "Starting stock") and an **optional** `skuPrefix` — SKUs default to the product slug (`CHIKANKARI-SUIT-M-OFF-WHITE`), with `-2`, `-3`… on the rare clash. Covered in `tests/integration/catalog-admin.test.ts`. (2) **"Sizes & colours" tab** (was "Variants"; "Images" is now "Photos"): Size, Colour, **In stock** (available, read-only, "+N in checkout" when > 0), Price, Status (Selling/Paused — renamed from "On sale/Off sale", which read like a discount), SKU last and muted; stock changes only via **"Manage stock →"**, which opens `/admin/inventory?product=<id>` (new filter, with a note naming the product and a "Show all stock" link). (3) **Variant edit**: the price override is behind a "Custom price for this size & colour" switch — off means the product price. (4) **Product form**: Name, Category, Status, Price, Original price (MRP), Description visible; slug ("Link name"), Featured, GST %, HSN and SEO title/description in a collapsed **More options** that opens itself if one of those fields has an error. GST still defaults to 18% as a placeholder — the business isn't GST-registered (docs/11 §29 #3); confirm the right treatment with a CA. (5) **Status wording**: Draft / **Live** / Archived (stored values unchanged). (6) **Hidden-category warnings**: the category picker marks "(hidden)", the form warns when a Live product sits in a hidden category, and the Products list tags such rows "hidden" / "not on store".

## Admin 2FA — removed, not built

Better Auth's `twoFactor()` plugin, its client-side counterpart (`twoFactorClient()` in `src/lib/auth-client.ts`) and the login form's TOTP challenge step (`login-form.tsx`) were all built during Phase 11, but no enrollment UI was ever built to let an admin actually turn 2FA on — so an admin account was never actually 2FA-protected in practice, only capable of being protected if enrolled directly in the DB. Rather than build that enrollment UI, the owner's call was to drop 2FA from scope entirely: the plugin, its rate-limit rule and the login form's challenge step have been removed. The `two_factor` table and `user.twoFactorEnabled` column remain in the schema (harmless, unused — no admin ever enrolled) but nothing reads or writes them anymore. Admin accounts rely on email/password + Turnstile + rate limiting only, same as before this was attempted.
