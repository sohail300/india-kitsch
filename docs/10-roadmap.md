## 26. Step-by-step roadmap: empty repo → production

**Done (Phase 0):**

2. **Read the Next docs that apply** in `node_modules/next/dist/docs/` before each feature. ✅ (ongoing — re-read the relevant guide before each new Next.js feature, not just once)
3. **Accounts (owner-owned, 2FA on):** GitHub, Vercel, Supabase, Cloudflare, Razorpay (KYC started), Resend, Sentry, Backblaze B2. ✅ (Cloudflare/Vercel currently under the developer's own account pending the owner-ownership migration — see docs/11 §27)
4. **Spike (Phase 0):** Vercel hello-world deployed; Drizzle transaction proven through the transaction pooler; `app`/`keepalive` schema lockdown migrated and RLS-verified; R2 presigned upload proven; cron Worker deployed and proven (keep-alive only so far); Cache Components confirmed with real evidence. ✅

**Part A — Backend, in order:**

5. **Foundation code:** Zod `env.ts`, logger, `money.ts`, Drizzle client, CI, migration workflow. ✅ (Phase 0 scaffolding already covers this — `errors.ts`, `tax.ts`, `ids.ts`, `rate-limit.ts` from the `server/lib/` layout in docs/02 still to come as the phases that need them arrive)
6. **Schema v1** (§4): every business table + Better Auth's tables, inside `app`; first real migration; local seed data; integration-test harness on Postgres. ✅ 24 tables migrated and verified against the real Supabase project (7 CHECK constraints, the `order_number_seq` sequence, all FKs); seed script run and verified (4 categories, 20 products, 192 variants, zero duplicate SKUs). Integration-test harness (real concurrency/rollback tests) still to come — deferred to step 9, where it's actually needed.
7. **Backups & monitoring wiring:** `pg_dump` every 12h → encrypted → R2 + B2, rolling retention; freshness alarm; Sentry; health endpoints. ✅ mostly — `/api/health` and `/api/health/deep` built and verified live (both confirmed dynamic, not prerendered); `scripts/backup-db.ts` written, with the encrypt→R2-upload→download→decrypt round-trip verified against real R2 (only `pg_dump` itself is unverified — not available on this Windows dev machine, only runs on Ubuntu/CI); `scripts/prune-backups.ts` + its pure selection logic (`scripts/lib/backup-retention.ts`) written and verified — 11 unit tests covering every tier and boundary, plus the real batch-delete call proven against R2; `.github/workflows/backup.yml` (every 12h) and `prune-backups.yml` (weekly) written (need GitHub secrets added before either can actually run); cron Worker's freshness threshold updated to match (14h) and redeployed, verified both failure and success paths against the real bucket. **Still open:** GitHub Actions secrets not yet added (blocks both workflows from running at all), Backblaze B2 account not yet created (blocks the off-Cloudflare copy — the script skips it and warns rather than failing), dedicated `ik-backups` bucket not yet split out from the images bucket (TODO before production, see scripts/backup-db.ts), Sentry not yet set up, Web Analytics deferred to Phase 10 (no real domain/traffic yet).
8. **Auth backend:** Better Auth + Drizzle; session helpers; `create-admin` script; admin 2FA; Turnstile + rate limits — verified via curl/API calls, no pages yet. ✅ mostly — `session.ts` (`requireUser`/`requireAdmin`) built and covered by 8 real integration tests (real signup/sign-in against the live DB, not mocks): no-session, garbage-cookie, disabled-account (checked live, not just at sign-in), customer-vs-admin, session isolation. Database-backed rate limiting (required for Vercel's stateless functions, not the default in-memory) confirmed via a real 6-request burst that correctly blocked at the configured limit, with the counter persisted in Postgres. Cloudflare Turnstile wired via Better Auth's official plugin, verified end-to-end with Cloudflare's own always-pass test keys (missing-token correctly rejected, valid dummy token correctly accepted) — real keys still needed before launch. `create-admin.ts` verified against the real DB (real password hash confirmed, not plaintext). Email verification/reset callbacks are wired but only log for now (`server/lib/email.ts`, a swappable `EmailSender` — Phase 8 supplies the real Resend implementation). Google OAuth wired but untestable without real credentials (conditional — activates automatically once `GOOGLE_CLIENT_ID`/`SECRET` exist). 2FA enrollment/enforcement UI is not built (that's Phase 10); the schema and challenge endpoints exist.
9. **Catalog & inventory backend:** product/category services and queries; search/filter logic; cache-tag design; **write the stock-reservation concurrency test now** (last-unit race, per docs/09 §20). ✅ — `catalog/{queries,service,schemas,cache-tags}.ts` and `inventory/{service,queries}.ts` built and covered by 21 real integration tests against a genuine local Postgres 16 (never Supabase, docs/09 §20), including this phase's centerpiece: 10 real concurrent `db.transaction()` calls racing for 3 units of stock, proving exactly 3 succeed, `reserved` never exceeds `on_hand`, overlapping multi-line carts touching the same two variants in opposite pick order don't deadlock, and an out-of-stock line rolls back an already-reserved earlier line in the same call. Also stood up the local/CI Postgres infrastructure this needed but didn't exist yet: `compose.yaml` + `scripts/local-db-init.sql` (stand-in `anon`/`authenticated` roles so the Supabase-specific RLS migration applies on vanilla Postgres too), `tests/setup/migrate-test-db.ts`, an injectable `dbHandle` argument on every catalog/inventory query so the same production code path is exercised in tests, and a `.github/workflows/ci.yml` Postgres service container replacing what had been an untested/broken `npm run test` CI step since Phase 3. New trigram-search migration (`drizzle/0004`) backs `ILIKE` name search. **Still open:** admin mutations that call `cache-tags.ts`'s `revalidateTag` (Phase 7); `"use cache"` components actually consuming these tags (Phase 10); sort-by-price only sorts on the product's base price, not the per-variant effective price (documented limitation, revisit if it matters at scale).
10. **Cart, pricing & coupons backend:** `pricing.ts`; `quoteCart`; coupon validation service. ✅ — `lib/pricing.ts` (moved here from the originally-planned `checkout/` since `quoteCart` needs it too and it's pure/DB-free) computes subtotal, a deterministic per-line discount allocation that always sums to exactly the coupon amount, GST-inclusive tax on the post-discount line total, and free-shipping-above-threshold on the _post-discount_ subtotal — a judgment call since docs didn't specify pre- vs post-discount; 11 unit tests including the exact rounding-remainder case. `coupons/{discount,validate,service,schemas}.ts` split pure math (unit-tested) from DB eligibility checks and the atomic conditional-`UPDATE` redemption (both integration-tested against real Postgres); proved the usage-limit race the same way as Phase 4's stock race: 10 concurrent redemptions against `maxUses: 3` leaves exactly 3 successes and 3 `coupon_redemptions` rows, the rest `CouponExhaustedError`. `cart/quote.ts` composes catalog + inventory + coupons + pricing into the advisory quote (docs/05 §8): merges duplicate lines, clamps per-line quantity at 10, reduces further to actual stock, flags archived/draft/out-of-stock lines as excluded-from-totals rather than throwing. Added `settings/{queries,schemas}.ts` for `store_settings`, since shipping numbers didn't exist anywhere yet — reads a real admin-set value if present, else a clearly-labelled placeholder (docs/11 §29 #5 — **still TBD, must be replaced with real numbers before Phase 6 goes live**). 41 new tests (11 pricing unit, 6 coupon-discount unit, 10 coupon-validate/redeem integration, 12 cart-quote integration, 2 settings integration), all against real infrastructure per docs/09 §20.
11. **Checkout & payments backend:** `createOrder`, Razorpay integration, **webhook route**, `markOrderPaid`, refunds; wire the reconciler into the existing cron Worker as its second trigger; **write the rollback and idempotency integration tests now**. ✅ — owner provided real Razorpay test-mode `RAZORPAY_KEY_SECRET`/`NEXT_PUBLIC_RAZORPAY_KEY_ID` (now required in `env.ts`, tightened from optional); `RAZORPAY_WEBHOOK_SECRET` stays optional — no webhook is configured yet, so `handleRazorpayWebhook` returns 503 until one exists. Built `orders/stateMachine.ts` (the full docs/06 §10 transition table plus one real edge the diagram doesn't show: `cancelled → paid`, for late payments), `checkout/createOrder.ts` (Razorpay order created outside the DB transaction; one transaction for order/items/payments/events + stock reservation + coupon redemption, in that order since `stock_movements.order_id` has a hard FK to `orders.id`), `payments/{razorpay,verify,webhook,reconcile,settle}.ts`. Closed the doc gap flagged in docs/12: late-payment reinstate-or-refund now runs from `payments/settle.ts`, shared by the webhook handler and the reconciler, not only the 10-minute sweep. Wired the reconciler into `cron-worker` as its second trigger (`*/10 * * * *`, told apart from the daily one via `event.cron`) — needs a real `APP_URL` before it can actually reach anything (placeholder for now, no production domain decided). 34 new tests (8 signature unit, 9 checkout-flow integration including a real concurrent last-unit race and the lazy-expired-reservation release, 16 payment-lifecycle integration covering `markOrderPaid`/`verifyPayment`/webhook idempotency/the full reconciler sweep including late-payment reinstate-and-refund from both the webhook and the reconciler, 1 env regression) — 139/139 total, Razorpay's HTTP mocked per docs/09 §20, everything else against real Postgres. **Still open:** real webhook secret/URL registration with Razorpay (owner-side), refunds admin action UI (Phase 7), Phase 8's confirmation/shipped/refunded emails (currently just the console `EmailSender`), owner-alert emails on a reconcile mismatch (currently logged only).
12. **Admin backend & media:** every admin service function; R2 upload route handlers (sign/commit) on the proven Phase 0 flow.
13. **Email/notifications backend:** Resend wiring; transactional email content; domain DNS.

## Verification (how we know the plan's outcome is right)

- **Phase 0 exit — done:** a real Drizzle transaction commits and rolls back correctly via Supabase's transaction pooler from a Vercel function; migrations and `pg_dump` run from CI; anon key cannot read any `app` table while the keep-alive ping succeeds; presigned R2 upload works from a browser; cron Worker successfully calls a protected endpoint; **Cache Components confirmed** (`cacheComponents: true` enabled; `next build` labelled a spike route `◐ Partial Prerender` with the expected `cacheLife` window, and repeated requests showed the cached part unchanged while the `connection()`-gated part changed every time — see docs/05 §7); CPU of dynamic routes measured (deferred — Vercel dashboard numbers, once there's enough built to be worth measuring, per the owner's call).
- **Phase 6 exit (checkout/payments backend):** the parallel-checkout test shows **no oversell**; webhook replay/tamper tests pass; Razorpay test-mode success, failure, closed-modal and refund flows verified end-to-end (via script/API calls, no UI needed yet); the reconciler recovers a deliberately dropped webhook.
- **Phase 9 exit (backend hardening — the gate before any UI work starts):** every service function and route handler has been exercised directly (script/curl/integration test) proving authz (customer A cannot reach customer B's data via a direct call; non-admin blocked from every admin action), no oversell under concurrency, webhook idempotency, and CSP/security headers are in place.
- **Phase 13 exit (launch checklist):** restore drill completed from an encrypted dump into a fresh Postgres, with the Razorpay reconciliation script run afterwards; backup-freshness and keep-alive alarms confirmed by triggering each once; CSP doesn't break Razorpay Checkout; Lighthouse budgets met on mobile; a live-mode ₹ test order placed and refunded; no live secrets in Preview; Vercel/Supabase usage thresholds and upgrade triggers documented.
