## 4. Database schema & relationships (Postgres on Supabase, via Drizzle)

Conventions: `text` primary keys (ULID, sortable) for app tables; **all money is `integer` paise** with a `_paise` suffix (max ≈ ₹2.1 crore per value, ample); `timestamptz` for times; `jsonb` for flexible blobs; `pgEnum` for statuses; `CHECK` constraints for invariants; foreign keys enforced; indexes listed per table. Migrations are generated by `drizzle-kit`, committed, and applied by CI (§18).

### Schemas and the Supabase REST API lockdown

A Postgres **schema** is a named folder of tables inside one database. Supabase's REST API (the "Data API") publishes only the schemas on its _exposed schemas_ list (default `public`) to anyone holding the public anon key. We need REST for one thing, the daily keep-alive ping (§18), so:

- **`app` schema (private):** every table in this document, including the Better Auth tables, lives here, declared in Drizzle with `pgSchema('app')` (`app.table(...)` instead of `pgTable(...)`; nothing else in the code changes). It is **not** in the exposed list, so REST cannot see it. Our server reaches it over plain SQL.
- **RLS as a second lock:** row-level security enabled on every `app` table with **no policies** (deny-all for the `anon` and `authenticated` roles), and privileges on `app` revoked from those roles.
- **`keepalive` schema (the only exposed one):** a single table `ping(id int)` with one row and a read-only policy. The ping (`GET /rest/v1/ping?select=id`) can therefore read nothing sensitive even if the anon key leaks. The `public` schema stays empty and is removed from the exposed list.
- `drizzle.config.ts` uses `schemaFilter: ['app', 'keepalive']` (both are ours to manage; `keepalive` holds the one-row table the REST ping reads).
- **Phase 0 checks:** using the anon key, a REST request for any `app` table must fail; and the ping must succeed. If Supabase's docs or a test show that SQL activity also prevents pausing, the Data API is disabled entirely instead (§29 #16).
- **Portability note:** the `app`/`keepalive` schemas and RLS itself are plain Postgres and dump/restore to any host cleanly. The one Supabase-specific bit is that the RLS grants/policies reference Supabase's `anon`/`authenticated` roles, which don't exist on a non-Supabase Postgres — a raw `pg_restore` onto Neon/self-hosted could throw a few harmless "role does not exist" errors on just those lines (`pg_restore --no-owner --no-privileges` skips them). The app's own connection is never affected by any of this, on Supabase or elsewhere, since Postgres exempts the table owner from RLS regardless of policies. If the project ever permanently leaves Supabase (§0 upgrade triggers), `keepalive` and its policies are simply dropped — they only ever existed to dodge Supabase's week-of-inactivity pause.

### Catalog

- `categories` — id, parentId (nullable, 1-level nesting in v1), name, slug (unique), description, imageKey, sortOrder, isActive. Idx: parentId.
- `size_charts` — id, name, unit (`cm`/`in`), columns (jsonb), rows (jsonb). Shown on PDP; admin edits as a table.
- `products` — id, slug (unique), name, description (plain text or sanitised markdown, never raw HTML), categoryId (single primary category; collections/tags deferred), sizeChartId?, `pricePaise` (selling price, GST-inclusive), `mrpPaise` (strike-through), `gstRateBps`, `hsnCode`, status (`draft`|`active`|`archived`), isFeatured, seoTitle, seoDescription, createdAt, updatedAt, publishedAt. Idx: (status, categoryId), (status, createdAt), trigram index on `lower(name)` for search.
- `product_variants` — id, productId, **sku (unique)**, `size`, `color`, `colorHex`, `pricePaise?` (null ⇒ product price; supports variant pricing), `mrpPaise?`, weightGrams?, isActive, sortOrder. **Unique (productId, size, color).** _Design note: explicit size/color columns instead of a generic option-type/option-value model. Simpler queries and filters, and exactly what a clothing brand needs; revisit only if non-apparel products arrive._
- `product_images` — id, productId, variantId? (color-specific images), r2Key, alt, width, height, sortOrder, isPrimary.
- `inventory` — **variantId PK**, `onHand`, `reserved`, updatedAt, with `CHECK (on_hand >= 0)`, `CHECK (reserved >= 0)`, `CHECK (reserved <= on_hand)`. Available = onHand − reserved.
- `stock_movements` — id, variantId, delta, reason (`reserve|release|sale|return|adjustment|restock`), orderId?, adminUserId?, note, createdAt. Append-only audit ledger. Idx: variantId, orderId.

### Commerce

- `addresses` — id, userId, label, fullName, phone, line1, line2, city, state (GST state code), pincode (6 digits), isDefault.
- `coupons` — id, code (unique, uppercased), type (`percent`|`fixed`), valueBps | valuePaise, minSubtotalPaise, maxDiscountPaise?, startsAt, endsAt, `maxUses?`, `usedCount`, perUserLimit?, isActive, with `CHECK (max_uses IS NULL OR used_count <= max_uses)`.
- `coupon_redemptions` — id, couponId, userId, orderId (unique), amountPaise, createdAt.
- `orders` — id, **orderNumber** (unique, from a Postgres sequence starting at 1001; displayed `IK-1001`), userId, **status** (§10), currency `INR`, `subtotalPaise`, `discountPaise`, `shippingPaise`, `taxIncludedPaise` (informational GST component), `totalPaise`, `refundedPaise`, couponCode (snapshot), **shipping address snapshot columns**, customerEmail/Phone snapshot, `razorpayOrderId` (unique), `idempotencyKey` (unique per user), `expiresAt` (pending-payment TTL), `courier`, `trackingNumber`, `trackingUrl`, `adminNote`, placedAt, paidAt, shippedAt, deliveredAt, cancelledAt, cancelReason, createdAt, updatedAt. Idx: (userId, createdAt), (status, createdAt), razorpayOrderId, expiresAt.
- `order_items` — id, orderId, variantId (SET NULL on delete), **snapshots:** productName, sku, size, color, imageKey, `unitPricePaise`, `mrpPaise`, quantity, gstRateBps, hsnCode, `lineTotalPaise`, `lineDiscountPaise`. Order history never changes when the catalog changes.
- `order_events` — id, orderId, fromStatus, toStatus, actor (`system|customer|admin:<id>|razorpay`), note, createdAt. Full audit trail.
- `payments` — id, orderId, provider, razorpayOrderId, razorpayPaymentId (unique, nullable until attempted), status (`created|authorized|captured|failed|refunded`), amountPaise, method, errorCode/errorDescription, createdAt. One order : N attempts. No raw payloads stored.
- `refunds` — id, orderId, paymentId, razorpayRefundId (unique), amountPaise, reason, status, createdBy, createdAt.
- `webhook_events` — **id = Razorpay event id (PK)**, type, receivedAt, processedAt, outcome. Idempotency/replay guard; rows older than 90 days pruned by the sweep job.

### Misc

`store_settings` (key/value: shipping fee, free-shipping threshold, GSTIN, seller state, contact info), `contact_messages`, `audit_log` (admin mutations: who/what/before/after).

### Relationships

`user 1─N addresses, orders` · `categories 1─N products` (self-ref parent) · `products 1─N variants, images` · `variant 1─1 inventory` · `variant 1─N stock_movements` · `orders 1─N order_items, order_events, payments, refunds` · `coupon 1─N redemptions` · `order 1─0..1 redemption`.

### Search

v1: `ILIKE` over name/description backed by a `pg_trgm` GIN index (available on Supabase), fine for thousands of products. Upgrade path: a `tsvector` column for ranked full-text search.

### Size budget (Supabase Free = 500 MB)

Rough estimate ≈ 5 KB per order including items, events, payments and indexes, so tens of thousands of orders before pressure, plus a base footprint for auth/catalog. Keep it down: no raw webhook/payment payloads, prune `webhook_events` after 90 days, images only in R2. An alert fires at 400 MB (§21).

## 11. Inventory / stock handling

- **Model:** `inventory(onHand, reserved)` per variant; `available = onHand − reserved`; append-only `stock_movements` ledger.
- **Reservation at order creation** (not at payment), **5-minute** hold, released on cancel/expiry, so two shoppers can't both pay for the last unit.
- **Atomicity with real transactions.** Inside a single Postgres transaction, per line, in **ascending `variantId` order** (consistent lock order prevents deadlocks):
  `UPDATE inventory SET reserved = reserved + :q WHERE variant_id = :v AND on_hand - reserved >= :q`
  If any statement changes 0 rows, throw `OutOfStock` and the whole transaction (order, items, coupon, other lines) rolls back. Under Postgres's default READ COMMITTED level, a concurrent conditional `UPDATE` re-checks its `WHERE` after waiting on the row lock, so two buyers of the last unit can't both succeed. The `CHECK` constraints are a backstop that makes an oversell impossible even if application code is wrong.
- **Coupon usage** uses the same pattern: `UPDATE coupons SET used_count = used_count + 1 WHERE id = :c AND (max_uses IS NULL OR used_count < max_uses)`; 0 rows ⇒ `CouponExhausted`.
- **Admin adjustments:** inline stock edit writes an `adjustment` movement with a required reason; a low-stock threshold surfaces on the dashboard; archived products keep their history.
- **Pooling:** the app connects through Supabase's **transaction pooler** (interactive transactions work; the connection is held only for the transaction's duration) with a small pool size, and **prepared statements disabled** (`prepare: false` with `postgres-js`, or use `pg`). Keep transactions short (a handful of statements), with no external calls inside. The Micro instance is small and shared, so keep queries indexed.
