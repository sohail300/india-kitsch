## 16. Database backup & recovery strategy

**Supabase Free has no backups and no point-in-time recovery**, so our own backups are the _only_ safety net. Defence in depth, so production never depends on one machine _or one vendor account_:

| Layer                                                | What                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   | Retention                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             | Purpose                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                        |
| ---------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **1. 12-hourly logical dump**                        | GitHub Actions cron **every 12 hours** → `pg_dump` (session-pooler connection) → **`age`-encrypted** file → the `backups/` prefix of the R2 images bucket for now (`ik-backups` as a genuinely separate, separately-scoped bucket is a TODO before launch — see `scripts/backup-db.ts`) **and** an off-Cloudflare copy (Backblaze B2 free 10 GB — bucket + scoped application key created and verified against the real bucket; still needs `B2_*` added as GitHub Actions secrets before the workflow can actually use them, see §19) | **Rolling retention, enforced weekly** by a separate job (`prune-backups.yml`, `scripts/prune-backups.ts`) so a bug in pruning can never take the backup job itself down: every backup for 7 days, then 1/day for 8–30 days, then 1/month for 31–365 days, then deleted. Keeps the object count bounded (~49 steady-state) regardless of cadence or how long the system's been running. The selection logic is pure and exhaustively unit-tested (`tests/unit/backup-retention.test.ts`) before it ever runs a real delete, the script defaults to a dry run, and it refuses to delete anything if fewer than 3 backups would remain. | Main recovery point. Encrypted because it contains customer PII. The DB is small and always awake, so a dump costs nothing. It also counts as daily database activity. Built in Phase 2 — `pg_dump` itself unverified until it runs on Ubuntu/CI.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                              |
| **2. Pre-migration dump**                            | The migration workflow (§18) takes an on-demand dump immediately before applying any migration                                                                                                                                                                                                                                                                                                                                                                                                                                         | Subject to the same rolling retention as #1 — it's uploaded to the same `backups/` prefix and the pruner doesn't distinguish by reason                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                | Substitutes for point-in-time recovery for the riskiest event: a bad migration                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                 |
| **3. Images — deliberately deferred, not built yet** | Eventually: weekly `rclone sync` R2 → B2; soft-delete grace period (§12)                                                                                                                                                                                                                                                                                                                                                                                                                                                               | continuous (once built)                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               | **Lower priority than the DB dump, on purpose.** R2 itself is already highly durable — this backup would only protect against losing the whole Cloudflare account, not R2 data loss. Product photos are also just inconvenient to lose (re-upload), not irreplaceable the way an order or customer record is — the original files almost always exist somewhere else too (photographer, owner's own storage), unlike DB rows which exist nowhere else. And right now there's nothing to back up: the seed script creates no `product_images` rows, so the bucket holds no real content yet. Build this once real product photos start getting uploaded (Phase 7 at the earliest, more likely Phase 10/13) — don't skip it before launch, just don't do it now. |
| **4. Code and schema**                               | GitHub (migrations committed); secrets inventory in a password manager                                                                                                                                                                                                                                                                                                                                                                                                                                                                 | n/a                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   | Rebuild the environment from scratch                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                           |
| **5. Razorpay**                                      | independent record of every payment                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                    | n/a                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   | Reconcile after any restore                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                    |

**Targets:** RPO ≤ 12 hours (data written since the last dump can be lost) — accepted as adequate at this order volume; a worst case is manually reconstructable from Razorpay's own payment records (docs/runbooks/restore.md step 5). RTO < 1 hour. Once real orders flow, the upgrade trigger in §0 (Supabase Pro daily backups, or Neon Launch history) exists to shrink this if it ever stops being adequate.

**Freshness alarm:** GitHub scheduled workflows can be delayed or silently disabled, so the daily Cloudflare cron Worker (which has an R2 binding) checks that the newest object in the `backups/` prefix is less than 14 hours old (12h cadence plus slack for the scheduler running late) and emails the owner if not — built and verified (both the failure and success path, against the real bucket) in Phase 2; the owner-email part is still a TODO for Phase 8, logged only for now. The dump job also records DB size (input to the 400 MB alert) — not yet built.

**Runbook** `docs/runbooks/restore.md`: (a) create a fresh Supabase project (or any Postgres, e.g. Neon), (b) decrypt the latest dump and `pg_restore` it, (c) update `DATABASE_URL` in Vercel and redeploy, (d) run the **Razorpay reconciliation script** comparing captured payments vs orders since the dump time and contact any customer whose paid order was lost. **Quarterly restore drill** into a scratch project or local Postgres.

## 18. Production deployment architecture

- **Environments** (Vercel Hobby has Preview + Production only; custom environments are a Pro feature _(verify)_):
  - `local`: Docker Postgres, Razorpay test keys.
  - `staging`: the `staging` git branch → a stable Preview deployment aliased to `staging.<domain>` _(verify branch-domain assignment on Hobby)_. Env vars scoped to Preview: the **second free Supabase project**, Razorpay **test** keys, `noindex`, Vercel deployment protection on.
  - `production`: `main` → Production. The production Supabase project, Razorpay **live** keys.
  - These two Supabase projects use both free slots.
- **Pipeline:** PR → CI (lint, typecheck, unit, integration against a Postgres service container, `next build`, Playwright) → merge to `main` → Vercel builds. **Migrations run first:** a GitHub Actions job takes a **pre-migration dump** (§16), then applies `drizzle-kit migrate` to the target database via the **session pooler** _before_ the new code is promoted. Migrations are backward-compatible (add first, remove later) so the still-running old version never breaks.
- **Domain/edge:** Cloudflare DNS with the app hostname **DNS-only** (grey cloud) pointing at Vercel, since Vercel provides its own CDN and TLS and double-proxying can cause redirect/cert issues _(verify against Vercel's Cloudflare guidance)_; `www`→apex redirect. `img.<domain>` → R2 public bucket domain, **proxied** (this is where Cloudflare's CDN is used). Turnstile site; Resend domain with SPF/DKIM/DMARC.
- **Scheduled jobs (Vercel Hobby cron is daily at best, so a tiny Cloudflare cron Worker in `cron-worker/`, Free plan):**
  - **Every 10 minutes:** `POST /api/cron/reconcile` with `Authorization: Bearer CRON_SECRET` (lost-webhook recovery, §9 step 7). Supabase Free stays awake and has no compute meter, so frequency is no longer constrained by the database.
  - **Daily:** the **keep-alive** for production and staging: `GET {SUPABASE_URL}/rest/v1/ping?select=id` with the anon key, hitting only the one-row `keepalive` table (§4, §14); plus the backup-freshness check (§16). A failed ping emails the owner _before_ the one-week pause.
  - A daily Vercel cron (`vercel.json`) hits `/api/cron/sweep` (orphan-image sweep, webhook-event pruning) as a backup path.
  - All cron endpoints are idempotent and reject requests without the bearer secret.
- **Connections:** the app uses the **transaction pooler** (`prepare: false`); migrations and dumps use the **session pooler** because CI runners are IPv4-only and Supabase direct connections are IPv6 _(verify)_.
- **Razorpay activation (start early; KYC takes days):** business docs/GSTIN/bank account, live keys, webhook URL + events (`payment.captured`, `payment.failed`, `order.paid`, `refund.processed`, `refund.failed`), auto-capture on. Razorpay requires live pages: Terms, Privacy, **Refund/Cancellation**, **Shipping policy**, Contact.
- **Region — decided: Mumbai.** The Supabase project is in the Mumbai region; the Vercel function region should be set to match (`bom1`).
- **Plan gate:** before public launch, the owner confirms the Vercel plan decision (§0, §29 #1).

Rules: never `NEXT_PUBLIC_` a secret; **never create or store the Supabase `service_role` key** (it bypasses RLS, and we don't use Supabase's client SDKs); `.env.local` gitignored, `.env.example` committed; `env.ts` validates on boot; rotate on any suspected leak; keep a secrets inventory (what/where/who/rotation) in a password manager.

### Implementation notes (B2 setup — verified against the real bucket)

- **`scripts/backup-db.ts`'s `uploadToB2` had two real bugs, both only surfaced by actually testing against the real bucket, not by reading the code:** it hardcoded `region: "us-west-000"` regardless of which region the bucket was actually created in (B2's S3-compatible API requires the signing region to match, so any bucket outside `us-west-000` — this one is `ca-east-006` — would have failed every upload with a signature error), and it passed `B2_ENDPOINT` straight to the S3 client without normalizing a missing `https://` scheme. Fixed by deriving the region from the endpoint hostname (`s3.<region>.backblazeb2.com`) instead of hardcoding it, and normalizing the scheme.
- **A real IPv6 connectivity issue, forced to IPv4:** the first live upload attempt timed out after ~30s (Node's dialer tried several of Backblaze's IPv6 addresses, each `ETIMEDOUT`, before ever falling back to IPv4), even though `curl` reached the same host over IPv4 in ~3s. `uploadToB2` now passes an explicit `NodeHttpHandler` with an IPv4-only `https.Agent` (`@smithy/node-http-handler`, added as a direct dependency rather than relying on it being an undeclared transitive one). This may be specific to the network this was diagnosed on rather than a general Backblaze problem, but forcing IPv4 is harmless wherever IPv6 already works, so it stays in unconditionally rather than only where it was observed to matter.
- **Verified with a real upload → download → byte-compare → delete round trip against the live `india-kitsch` B2 bucket** (a throwaway script exercising the same `normalizeB2Endpoint`/`b2RegionFromEndpoint`/client-construction logic now in `uploadToB2`, deleted after use — same "`_tmp-*` spike, since removed" pattern this file's own top comment already documents for the original R2/B2 code). `pg_dump` itself is still only verified on Ubuntu/CI, per that same comment — this only proves the upload half.

## 21. Monitoring & logging

- **Logs:** structured JSON logger with request id, route, user id (not email), duration; never log secrets, card/UPI data or full payloads. Vercel Hobby runtime-log retention is short _(verify)_, so **don't rely on it**: errors go to Sentry, and business-critical events are also written to an `audit_log`/events table.
- **Errors:** Sentry free tier (official Next.js SDK).
- **Uptime:** an external monitor (Better Stack / UptimeRobot free) hits `/api/health` (app liveness, no DB) every few minutes, and `/api/health/deep` (`SELECT 1` through the pooler) every ~5 minutes; the database is always awake on Supabase Free, so this costs nothing.
- **Business alerts (email to owner):** webhook signature failures, payment amount mismatch, paid-at-Razorpay-but-order-cancelled, reconciler discrepancies, confirmation-email failures, **backup job stale (> 8 h)**, **keep-alive ping failed**, low stock, **DB size > 400 MB**, Vercel usage nearing Hobby allowances (checked from dashboards weekly until automated). Supabase also emails before pausing a project; those emails must reach the owner.
- **Analytics:** Cloudflare Web Analytics; Razorpay dashboard for payment health.
