## Design Context

### Users

The India Kitsch admin panel (`src/app/admin/`) is used by exactly the store owner plus one other admin (docs/11 §29 #9 — no public admin signup). It's an internal, back-office tool for running a D2C clothing e-commerce brand day to day: processing orders, adjusting stock, editing products/variants/images, managing coupons, handling customers, and store settings. Used at a desk during business hours, not on the move.

### Brand Personality

The storefront-facing India Kitsch brand is playful/maximalist ("kitsch" is the whole point), but the **admin tool deliberately does not inherit that voice** — it's a working tool, not a customer touchpoint. Three words for the admin UI specifically: **sharp, efficient, no-nonsense.** Fast to scan, fast to act on, nothing decorative that doesn't earn its place.

### Aesthetic Direction

- **Not** a faithful recreation of the Horizon-UI-style reference screenshots in `public/` (indigo/white SaaS dashboard) — that direction was tried and rejected as generic/AI-templated, despite being modeled on a real reference. Horizon UI is itself one of the most-cloned free admin templates, which is part of why it read as generic.
- **Primary reference: [Untitled UI](https://www.untitledui.com/)** — restrained neutral-gray palette, precise typography and spacing, deliberate/refined component patterns (tables, badges, empty states, forms) rather than a stock "AI dashboard" look. The goal is Untitled UI's _level of craft and restraint_, not a literal clone of its components.
- **Light mode only** — daytime, desk-based workflow.
- No hard brand-color mandate for the admin tool; pick a restrained accent that reads as intentional, not a default indigo/purple AI-dashboard hue.

### Accent colour candidates

- **Current accent:** the rust `--primary: oklch(0.5 0.15 40)` in `src/app/globals.css`.
- **Candidate — amber `#F8A325`** (tried on the Settings page on 2026-09-25 as a page-scoped override, then reverted; kept here for later). It's a light colour, so it needs **dark text on solid fills** — white text fails contrast. The values that were used:
  - `--primary: #F8A325`
  - `--primary-foreground: oklch(0.25 0.05 60)` (dark text on amber buttons)
  - `--accent: color-mix(in oklch, #F8A325 14%, white)` (light tint for icon boxes, soft buttons)
  - `--accent-foreground: oklch(0.45 0.12 60)` (deeper amber for accent text/icons)
  - `--ring: #F8A325`
  - To adopt it app-wide, set these in `globals.css`'s `:root` rather than per page, and re-check contrast on the `soft` button and status badges.

### Design Principles

1. **Density and speed over decoration.** This is a tool used many times a day by the same one or two people — optimize for scan speed and action speed (e.g. inline actions, keyboard-friendly tables), not first-impression delight.
2. **Restraint over ornament.** No side-stripe accent borders, no gradient text, no glassmorphism, no hero-metric-card clichés. Follow the `impeccable` skill's DON'T list strictly.
3. **One clear accent, used rarely.** 60/30/10 weighting — mostly neutral surfaces and text, a single accent color reserved for genuinely primary actions and key status, not sprinkled everywhere.
4. **Real component discipline.** Use shadcn/ui + base-ui primitives consistently and idiomatically (already in `package.json`) — the previous pass under-used them rather than needing a different library.
5. **Every state considered.** Empty, loading, and error states for every table/list, not just the happy path — this is a tool for someone who'll hit those states daily (e.g. "no orders today" vs. "no orders match this filter").

### Established patterns (admin)

Concrete conventions settled while building out the Coupons and Customers pages (2026-09-25). Each one applies the principles above; new admin screens should follow them rather than re-deciding. Architecture/implementation detail lives in `docs/07-images-and-admin.md` §13 and its implementation notes.

**Lists and tables**

- **Everything happens on the server.** Search, filters, sorting and pagination are all SQL (`WHERE` / `ORDER BY` / `LIMIT`/`OFFSET`) driven by URL params, never client-side over a full dataset. A page loads only its own rows, and every view is bookmarkable and back-button-safe. _Why:_ client-side filtering or sorting only ever sees the 20 rows on screen, and silently wrong results are worse than none.
- **20 rows per page everywhere** — one constant, `ADMIN_PAGE_SIZE` (`server/modules/admin/pagination.ts`), shown through `AdminPagination`.
- **Filter bar layout:** search input with a leading search icon → status `Select` → **Search** button (`soft` variant, search icon) → ghost **Clear**, shown only while a filter is active. Filters apply on submit, not on every keystroke.
- **Two distinct empty states:** "No X yet" (nothing exists — with a hint on how to create one) vs. "No X match these filters" (filters hid everything — search icon, suggest changing the filters). Principle 5 in practice: these are different situations and the user needs to know which one they're in.
- **Sortable columns are opt-in, not universal.** Only columns where an order is meaningful: not mixed-unit values (percent vs. flat ₹ discount) and not columns a filter already covers (status). Header shows a faded ↕ when sortable, ↑/↓ on the active column, and `aria-sort` for screen readers.
- **Sort behaviour:** text columns start A→Z, numbers and dates start high/newest-first; clicking the active column flips it; a new sort returns to page 1; the default sort is omitted from the URL; empty values ("No cap", "—", no orders yet) **always sort last** in both directions; `id` is the tiebreaker so equal values keep a stable order across pages. The sortable set is a fixed allowlist per page — an unknown `?sort=` falls back to the default.
- **Only the row's identifier is a link** (customer name, order number) — accent colour + underline on hover. Whole-row click targets were removed: they fire on accidental clicks and conflict with inline controls (switches, edit buttons) in the same row.
- **Hand-ordered lists reorder by dragging a grip handle** (`SortableDataTable`), never ↑/↓ buttons: it's direct, and the handle keeps the rest of the row's controls clickable. Keyboard (Space, ↑/↓) and touch work too. Such lists still get search, column sorts and pagination, but **dragging only exists in the manual (store) order view** — sorted by any other column, the handles disappear and a note offers "Back to store order". Dragging works on any page or within search results: the dragged rows swap among the positions they already hold.
- **Missing values render as a muted "—"** (or a muted word when it carries meaning: "No cap", "No limit", "Unlimited"), never blank.

**Status and attribution**

- **Show the effective status, not the raw flag.** Coupons show Live / Scheduled / Expired / Used up / Inactive, derived in one SQL `CASE` that both the badge and the status filter use, instead of just the on/off switch — "is this working right now?" is the question the admin actually has. The raw switch stays as its own column for acting on.
- **Badges** (`status-badge.tsx`) are small `rounded-md` tinted pills using the semantic tones (success / info / warning / destructive / neutral) — slightly squared rather than full pills, to sit with the rest of the squared-off UI.
- **Say who did it.** Creation and disabling show "by \<admin email\>" with a timestamp in a muted second line (coupons' Created column; a disabled customer's status). Admin-side accountability is cheap to show and answers the first question when something looks off.

**Actions and confirmation**

- **Any state change with real consequences asks first — in both directions** (activate _and_ deactivate a coupon; disable _and_ re-enable a customer; sign out). A switch doesn't flip until the dialog is confirmed. Dialog titles name the object ("Deactivate DIWALI25?") and the description says what will actually happen. The red `destructive` style is reserved for genuinely destructive actions (disable account), not for every confirmation.
- **Visibility cascades, deletion doesn't.** Hiding something hides everything that only makes sense under it (a hidden category hides its products from the storefront), but never deletes anything — showing it again restores everything. The confirmation says exactly that, with the count of what's affected ("its 5 products can't be browsed or bought. Nothing is deleted").
- **Toasts**: 3 s, top-right, tinted with the theme's own status tokens (soft background, stronger border and text) rather than Sonner's saturated defaults.

**Buttons and accent use** (principle 3)

- Solid **primary** (the rust accent) only for the page's main action ("New coupon", "Create coupon").
- **`soft`** variant — light accent tint with a `primary/30` border — for secondary-but-important actions like Search. Visible without competing with the primary action.
- **Ghost** for low-emphasis navigation and resets: back buttons, Clear, "View all orders →".
- **Pointer cursor** on every interactive control, including switches.

**Stock editing** (decided 2026-09-25, revised the same day)

- **Stock can be adjusted in two places, through one dialog.** Each size & colour row on the product page has an "Adjust stock" button, and the Inventory page is the store-wide stock view (low stock, search by name/SKU, bulk restocking). Both open the **same** Adjust dialog — reason required, every change in the stock history — so the numbers can't diverge. _History:_ first decided as "stock only in Inventory, read-only on the product" (2026-09-25); the owner then asked for per-size stock editing on the product page too, so the rule is now "one dialog", not "one page".
- The sidebar follows the catalog's own structure: **Categories → Products → Inventory**.

**Forms and dialogs**

- **Owner words, not system words.** "Sizes & colours" not "Variants"; "In stock" / "In checkout" / "In hand" not "Available" / "Reserved" / "On hand" (in hand = in stock + in checkout; explained by the ⓘ on Inventory's In stock column); product status **Draft / Live / Archived** (not "Active", and not "Hidden" — that word belongs to categories); "Original price" not "MRP"; "Link name" not "slug"; "Custom price" not "price override"; a size & colour is **Selling / Paused**, not "Active" (and not "On sale / Off sale", which reads like a discount). Technical identifiers (SKUs) are generated, shown muted, never asked for.
- **Multi-part creation is a numbered stepper, not hidden tabs.** Show every step up front (1 → 2 → 3) so the owner sees the whole job; lock steps that need an earlier one saved, and let completed steps be revisited. Each step ends with an explicit "Next: <step name> →" / "Finish" (never a vague "Save & continue").
- **Progressive disclosure for rare fields**: keep the everyday fields visible and put the rest in a collapsed "More options" — which must open by itself when one of its fields has a validation error.

- **Don't ask what has a sensible default.** New coupons are always created enabled; the switch lives on the list, not in the create form. Fewer fields = faster, fewer mistakes.
- **Immutable-after-creation fields get a note, not a subtitle** — an `Alert` with an ⓘ icon and a muted background ("Type and value can't be changed after creation."), marked `role="note"` so screen readers don't announce it as an alert.
- **Hints are rare and short**, one muted line directly under the field they explain ("Leave empty to make it usable right away.").
- **Dates are date-only** wherever time-of-day doesn't matter to the admin (coupon validity), picked with `DatePickerField` — the same Popover + Calendar pair as the dashboard's custom range — with a Clear action. A start date means from the start of that day; an end date is inclusive, through the end of that day. Pickers prevent choosing an end before the start.
- **Dialog sizing:** header and footer stay fixed, only the field area scrolls, and the dialog grows to the window height before scrolling at all. Wide forms with side-by-side fields get a wider dialog (`sm:max-w-xl`).

**Layout and display**

- **Cards are elevated consistently:** `rounded-2xl` + `ring-1 ring-border` + `shadow-sm` (dashboard, settings, customer detail).
- **Detail pages** get a ghost "← Section" back button above the page header.
- **The desktop sidebar is sticky** (full viewport height, its own scroll if needed) — navigation and the account/sign-out footer never scroll away with the content.
- **All dates are shown in store time (`Asia/Kolkata`)** via `_lib/format-date.ts` — "Sep 25, 2026", or "Sep 25, 2026 · 3:40 pm" where the time matters — because admin pages render on the server and would otherwise use the host's timezone (UTC in production).
